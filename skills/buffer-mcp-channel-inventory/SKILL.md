# Buffer MCP: 채널·도구 조회는 읽기 전용으로, 순서대로

- 조회 요청이면 게시물·아이디어·템플릿을 만들지 않는다. 사용자가 "게시/초안 생성은 하지 마"라고 하면 `create_*`, `edit_post`, `delete_*` 호출 금지.
- 순서: `ToolSearch`로 `select:mcp__buffer__get_account,mcp__buffer__list_channels` 로드 → `get_account`로 `organizations[].id` 확보 → 그 ID로 `list_channels`. 채널 ID를 추측하지 않는다.
- 사용자가 도구 목록을 명시하면(예: "introspect_schema, get_channel, get_account만 사용") 그 목록이 경계다. 목록 밖 도구(예: `list_channels`)는 읽기 목적이어도 호출하지 않는다. 필요한 ID가 목록 밖 도구로만 얻어지면 추측하지 않고 "ID 미확보, get_channel 미호출"로 막힌 항목에 적는다. "읽기만" 또는 "list_posts만 사용"처럼 목록 없이 좁히기만 하면 쓰기 금지로 읽는다. `list_posts`는 `organizationId`(24자 hex)가 필수이므로 조직 ID가 없으면 읽기 전용 `get_account`를 먼저 호출해 얻는다. 사용자가 `organizationId`와 `channelIds`를 직접 주면 `get_account`·`list_channels`는 생략하고 `ToolSearch`로 `select:mcp__buffer__list_posts`만 로드해 바로 조회한다(2026-10-27 실측: 이 경로로 draft 2건 정상 조회). 사용자에게 조직 ID를 되묻는 것은 `get_account`가 실제로 권한 거부된 뒤에만 한다. 초안 생성도 같은 원리다: 사용자가 `channelId` 두 개를 직접 주고 도구 목록(`get_channel`, `create_post`, `get_post`)을 명시했으면 `get_account`·`list_channels`를 생략하고 `ToolSearch`로 그 도구만 로드한다(2026-10-27 실측: 이 경로로 Threads·Instagram 초안 2건 성공).
- Buffer MCP 도구가 세션에 로드되지 않아 `ToolSearch`로도 안 올라오면, 읽기 전용 조회를 `claude -p`로 돌린다: 프로젝트 폴더에서 `claude -p "<조회 지시, 수정·삭제 금지>" --allowedTools "mcp__buffer__get_post" "mcp__buffer__list_posts" < /dev/null > <scratchpad>/result.txt`. 허용 도구 이름은 쓰기 도구를 제외한 것만 적는다(2026-10-27 실측: draft id·assets·altText 조회 성공).
- 쓰기 금지 조회에서 도구 스키마를 로드할 때는 키워드 검색(`ToolSearch`에 `+buffer get_post list_posts` 같은 질의)을 쓰지 않는다. 키워드 질의는 `delete_post`·`edit_post` 스키마까지 세션에 올려 금지 도구가 노출된다. 반드시 `select:mcp__buffer__get_post,mcp__buffer__list_posts`처럼 정확한 이름만 적는다.
- 게시물 조회 표는 `id | 채널 서비스 | status | 생성 시각 | assets 개수` 열로 만든다(`channelService`, `status`, `createdAt`, `assets` 배열 길이). `list_posts`는 `channelIds`, `status=[draft]` 필터와 `sort:[{field:"createdAt",direction:"desc"}]`를 쓴다(2026-10-27 오류 없이 통과). `assets`는 list_posts 응답에 이미 있으므로 개수만 필요하면 get_post를 부르지 않는다.
- 특정 게시물 세부 점검(assets 순서·url 호스트·mime·width/height·altText, 캡션 길이, 해시태그 개수)은 `ToolSearch`로 `select:mcp__buffer__get_post`를 로드해 조회한다. url은 기본적으로 호스트만 적고 경로·쿼리는 뺀다. 단 사용자가 이전 첨부와의 id 비교를 요구하면 각 url의 마지막 경로 id를 전부 적는다(쿼리는 그대로 뺀다). 비교할 이전 id 목록이 대화에 없으면 '이전 id 없음, 비교 불가'로 적고 이전 목록을 요청한다. 해시태그 개수는 `text` 끝 줄의 `#` 토큰을 센다. 글자 수를 python으로 못 재면 눈으로 어림한 값임을 '추정'으로 명시한다.
- 사용자가 준 post id를 찾을 수 없어 보이면 UI 저장으로 id가 바뀌었다고 단정하지 말고 먼저 `get_post`로 존재를 확인한다(2026-10-27: UI 저장 후 `6ae06a…` id 유지, `updatedAt`만 갱신). 정말 없을 때만 list_posts 결과에서 `createdAt`이 가장 최근인 draft를 `get_post`로 조회한다.
- 사용자가 "표로만"처럼 출력 형식을 지정하면 그 형식을 따르고 답변 첫 줄 조직 이름 머리말은 생략한다. 지정이 없으면 첫 줄에 조직 이름을 밝힌다.
- `get_account`가 권한 거부되면 조직 ID를 얻을 수 없다. 로컬 파일·메모리를 grep해 ID를 찾아 넣지 않는다(Bash도 거부된다). 채널 표는 보류하고 권한 허용 또는 조직 ID 직접 전달을 요청한다. ID가 필요 없는 스키마 요약은 계속 진행한다.
- 답변 첫 줄에 사용한 조직 이름과 계정 ID를 밝힌다. 사용자가 `organizationId`를 직접 주고 `get_account`를 생략했으면 첫 줄에 그 ID를 적고 "조직 이름은 get_account 미호출로 확인하지 않음"이라고 명시한다. 이름을 추측해 쓰지 않는다.
- 채널 표는 `id | 서비스 | 이름 | 상태(isDisconnected, isLocked)` 열로 만든다.
- 플랜 한도(`limits.channels`, `limits.scheduledPosts`)는 get_account 응답에 있으니 함께 적는다.
- 레이트 리밋은 Buffer 클라이언트 전체가 공유한다. 응답마다 붙는 `rateLimit` 값을 확인하고 조회를 반복하지 않는다.
- "사용 가능한 도구 목록"은 세션에 로드된 `mcp__buffer__*` 이름만 근거로 쓴다. 로드되지 않은 도구는 넣지 않는다.
- 스키마·기능 질문("mutation 뭐 있어?", "연결 URL 만들 수 있어?", "미디어 제약 정리")은 `ToolSearch`로 `select:mcp__buffer__introspect_schema`를 로드해 인자 없이 한 번만 호출하고, 응답의 `type Mutation {…}` 블록을 읽는다. 도구 description 원문이 필요하면 `ToolSearch`로 `create_post`도 로드해 그 description을 읽는다. 조회 전용 요청이면 `execute_mutation`은 호출하지 않는다.
- 플랫폼 한도(글자 수, 해시태그 개수, 이미지·영상 용량·비율·포맷·개수, 캐러셀 장수)는 introspect_schema에 숫자로 없다. 스키마에는 `LengthRule`, `FileSizeRule`, `CountRule`, `FormatRule`, `DurationRule` 타입만 있고, 값은 `configuration(input:{organizationId})` 쿼리(`services[].content[].rules`, 기준 스키마 해석이며 실응답 미검증)에 있다. 이 쿼리는 `execute_query`로만 호출 가능하므로 사용자가 허용 도구를 좁혔으면 호출하지 않고 "스키마 타입만 확인, 숫자 미확보"로 보고한다. `ImageMetadata.altText`/`ImageMetadataInput.altText`는 alt text 필드, `OrganizationLimits`에는 채널 외 한도 필드가 더 있으나 `get_account` 응답에는 `channels`, `scheduledPosts`, `tags`, `ideas`, `members`만 값이 있다.
- 서비스별 content 규칙 조회(읽기 전용, `execute_query`만): `configuration(input:{organizationId})` → `services[].content[]`에서 `configurationContentTypes`, `supportedProperties`, `rules { __typename property ... on LengthRule { maxLength } ... on CountRule { min max } ... on FileSizeRule { maxMegabytes } ... on DurationRule { maxDurationSeconds } ... on FormatRule { allowedFormats } ... on ExclusiveRule { conflictsWith } ... on RequiresRule { requires } }`를 한 번에 요청한다. 7개 rule 타입 fragment를 모두 넣어야 '없음'이 응답에 실제로 없다는 뜻이 된다. `ConfigurationContentType`은 `comment`·`post`·`reel`·`story` 4종뿐이라 carousel·thread 종류는 없다(`thread`는 `ContentProperty` 값). 사용자가 "carousel별 한도"를 물으면 이 점을 먼저 알린다. 숫자는 `comment` 종류 기준이며 게시 캡션 한도로 해석하지 않는다(2026-10-27: instagram business 2196, threads profile 500, instagram profile은 `content: []`). 규칙 없는 조합은 표에 '없음'으로 적고 추측하지 않는다.
- 미디어(assets)는 업로드할 수 없고 URL로만 넘긴다. `create_post` 도구 description(assets 파라미터)의 원문: "url: Direct http(s) file URL that is publicly downloadable: not a local file path, not a share or preview page, not a temporary host that expires." 따라서 로컬 파일 경로·공유/미리보기 페이지·만료되는 임시 호스트 URL은 쓰지 않는다. 스키마에 upload·media·asset 이름의 Mutation은 없다(2026-10-27 확인). `ImageAssetInput`은 `url: String!`, `metadata: ImageMetadataInput`, `thumbnailUrl`이고, `IdeaMediaInput.url`에는 공개 URL 제약 문구가 없으니 아이디어 미디어에 같은 기준을 적용한다. 제약 문구는 `create_post` description에만 있고 GraphQL 타입에는 없다.
- 2026-10-27 스키마 기준 Mutation 22개: createSnippet, deleteSnippet, updateSnippet, createPost, deletePost, editPost, movePostInQueue, addPostToContentItem, createContentItem, createContentItemDraft, deleteContentItem, promoteContentItemDraftToPosts, removePostFromContentItem, updateContentItem, updateContentItemDraft, createTag, deleteTag, updateTag, createPostTemplate, deletePostTemplate, updatePostTemplate, createIdea.
- createPost 메타데이터(instagram/threads), 이미지 assets, mode·schedulingType, 초안 생성 방법은 `references/create-post-schema.md`를 먼저 본다(2026-10-27 조회본, 호출 검증 전).
- 채널 연결/추가 mutation과 OAuth 연결 URL 필드는 스키마에 없다. 채널 연결은 publish.buffer.com 웹에서 직접 하고, 연결 후 `list_channels`로 ID를 확인한다. 이미 연결된 Threads 채널은 `Service` enum과 `ThreadsPostMetadataInput`으로 게시 가능하다.
- 초안 생성(`create_post`) 전에 채널 타입을 `get_channel`로 확인한다. Instagram 개인 프로필 채널은 `schedulingType=notification`만 허용되고, `automatic`이면 HTTP 400으로 거부된다(거부 문구: "Instagram personal profile channels require notification scheduling"). `automatic`은 비즈니스 계정에만 쓴다. Instagram 게시는 이미지/동영상 asset이 필수라서 텍스트만으로는 거부된다고 미리 본다. 단 2026-10-27 실측: `assets: []`인 Instagram 초안 생성(`metadata.instagram.type=post`, `shouldShareToFeed=true`, `schedulingType=notification`)은 성공했고 `status: draft`, `error: null`이었다. 후속 실행에서 `get_channel`을 먼저 호출해 개인 프로필임을 확인했다(`type: profile`, `descriptor: Personal Account`, `metadata.defaultToReminders: false`). 그 뒤 `notification`+`assets: []`로 생성하자 `status: draft`, `dueAt`·`sentAt` null, `sharedNow` false, `error` null로 `get_post` 대조를 통과했다. 게시·예약 시 asset 거부 여부는 아직 검증되지 않았다.
- Threads 연결 게시물: 바깥 `text`는 thread 첫 항목 텍스트와 같아야 하고, `metadata.threads.thread` 배열에는 1번 항목부터 전부 넣는다. 사용자가 "배열에는 2~5번만"이라고 지정해도 Buffer 도구 규격을 따르고, 편차는 보고에 적는다.
- 생성 직후 `get_post`로 대조한다: `status`가 draft인지, `dueAt`/`sentAt`이 null인지, `sharedNow`가 false인지, `threadCount`, 게시물별 text가 보낸 값과 같은지. 이 대조 결과만 "저장 확인됨"이라고 보고한다.
- 초안 생성 절차(고정): ① `ToolSearch`로 `select:mcp__buffer__create_post,mcp__buffer__get_post` 로드 ② `get_channel`로 채널 타입 확인 ③ `references/create-post-schema.md`를 읽는다(2026-10-27 실측 세션에서 이 단계를 건너뛰고 바로 `create_post`를 호출했다. 후속 실행에서는 ①→②→③→④→⑤ 순서대로 수행해 Threads 6게시물 초안과 Instagram 초안을 모두 `status: draft`로 저장 확인했다) ④ `create_post`를 `saveToDraft: true`, `mode: addToQueue`로 호출 ⑤ `get_post` 대조. 사용자가 준 문구는 한 글자도 바꾸지 않는다.
- 보고 형식: 생성 성공 여부, post id, status, 글자 수, 오류 원문. 글자 수는 Bash(python) 승인이 있어야 측정된다. 거부되면 "추정"이라고 쓰고 해시태그 annotation indices 같은 간접 값으로 적지 않는다. get_post 대조를 눈으로만 했으면 "눈검사"라고 명시한다.
- 기존 초안 문구 갱신(edit_post) 절차(고정): ① `ToolSearch`로 `select:mcp__buffer__get_post,mcp__buffer__edit_post` 로드 ② `get_post`로 `status`, `schedulingType`, `shareMode`, `metadata`(instagram: type·shouldShareToFeed / threads: type·thread 개수) 원본을 읽는다 ③ `edit_post`에 `saveToDraft: true`와 `text`를 넣는다. edit_post는 부분 병합이 아니라 게시물 전체를 다시 검증하므로, 바꾸지 않는 metadata 필드도 같은 값으로 다시 보낸다. 빠뜨리면 거부되거나 값이 바뀐다. ④ 생략한 `mode`·`schedulingType`·`assets`는 기존 값을 유지한다(`assets: []`는 비운다, 생략은 유지). ⑤ edit 후 `get_post`로 재조회해 `status: draft`, `dueAt`/`sentAt` null, `sharedNow` false, `threadCount`, 게시물별 text를 보낸 값과 대조한다. Threads는 바깥 `text`를 1번 항목과 같게, `metadata.threads.thread`를 전체 교체한다(2026-10-27 실측: 6게시물 → 5게시물 교체, 재조회 시 `threadCount: 5`, 문구 일치, draft 유지). Instagram 캡션 교체도 같은 절차로 `schedulingType: notification`, `shouldShareToFeed: true`, draft 유지를 확인했다.
- 요청한 초안 개수와 문구 섹션 수가 다르면(예: "두 개" 요청에 한 섹션만 있음) 만들기 전에 빠진 항목을 보고에 먼저 적는다.
- 사용자 지시와 도구 요구가 충돌하면 임의로 우회하지 않는다. 거부 응답은 오류 문구와 HTTP 코드를 원문 그대로 보고하고 멈춘다.
- `Channel.allowedActions`의 `reconnectChannel`·`removeChannel`은 권한 enum 값이지 실행 가능한 mutation이 아니다. `Configuration.channels[].authorizationStatus`는 조회만 된다.
- "없다"는 답에는 스키마 조회 날짜를 붙인다. Buffer 스키마는 바뀔 수 있다.
- 삭제(영구 삭제)는 에이전트가 직접 호출하지 않는다. 사용자가 요청해도 Buffer 웹 경로와 대상 post id를 안내해 사용자가 직접 지우게 한다. 삭제 전에는 get_post로 대상 내용을 확인한다.
- 카드 이미지 첨부: API는 공개 URL만 받고 업로드 mutation이 없다. 로컬 카드는 `buffer-draft-media-attach` 스킬로 Buffer 웹 작성기에 직접 업로드한다(2026-10-27 실측: 8장 첨부, 공개 호스팅 불필요). 이미지 없는 게시의 거부 여부는 실측 전이므로 미검증으로 적는다.
- 문구 갱신 후 대조는 에이전트의 요약이 아니라 코드로 한다. 원본 파일에서 마커 사이 문구를 추출해 get_post 재조회 값과 비교한다. 눈검사만 했으면 그렇게 적는다.
